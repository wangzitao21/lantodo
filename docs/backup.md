# 存储与备份

## 为什么 SQLite 的备份里是 JSON？

本机存储格式和数据交换格式解决不同问题。LanTodo 用 SQLite 提供事务、单文件存储和一致性校验；用 ZIP + JSON 导出可校验、可去重的历史版本，以便在另一台设备上合并恢复。备份不必是 `.sql`，SQL 脚本也不是 SQLite 数据库文件。

| 内容 | 保存位置 | ZIP 导出是否包含 |
| --- | --- | --- |
| 附件原件（清单与回收站仍引用且有效） | 数据库旁的 `attachments/` | 是 |
| 待办、备注、日期、完成状态 | SQLite `revisions` | 是 |
| 全部修改历史、删除记录、冲突分支 | SQLite `revisions` | 是 |
| 设备证书私钥、名称、配对、同步间隔 | SQLite `metadata` | 否 |
| 从旧资料转换时保留的自动备份字节 | SQLite `metadata` | 否 |
| Android 草稿及少量界面偏好 | 系统私有设置 | 否 |
| Android 通知、电池等权限 | Android 系统管理 | 否 |
| Windows 自定义数据位置 | EXE 旁的 `LanTodo.location` | 否 |

ZIP 导出统一清单的全部内容；回收站可用原件会保留，失效状态写入 manifest 的 invalidAttachments，失效原件不进入备份。ZIP 包含 `manifest.json`、`revisions/<内容哈希>.json` 和 `attachments/<文件哈希>`。原件尚未同步完整时不会生成完整备份。每个 JSON 是一个不可变历史版本，不是一份重复的完整清单。恢复会检查格式、内容哈希、父版本和引用关系，再通过事务合并；相同版本不会重复导入，本机新修改不会被整库覆盖。旧备份继续可用。

因此保留现有格式。界面中的操作名为“导出全部清单与历史”，明确它是**数据备份**，不是含私钥和配对的数据库镜像。

## 如何备份与恢复

在“备份与恢复”导出 `.lantodo.zip`，保存到独立磁盘或可靠备份位置。恢复时选择“从备份合并恢复”。换设备后重新配对。文件未加密，并包含已删除内容的历史，按私人资料保管。

Windows 的完整本机快照：先在托盘选择“退出 LanTodo”，确认应用完全退出，再复制整个程序 / 数据目录，包括 `LanTodo.sqlite`、`attachments/`、`attachment-index.json` 和 `spaces/`。只复制 SQLite 会遗漏原件、附件状态和其他空间。如果仍有事务日志，应一并保留并先排查非正常退出，不在数据库写入时直接复制文件。自定义位置还需记录位置或保存 `LanTodo.location`。整库含设备私钥，只用于同一设备资料的恢复或便携移动；在另一台同时运行的设备上请使用 ZIP 合并恢复，避免身份重复。

Windows 数据库固定存于 EXE 旁，附件放在 根目录 attachments/<原文件名>，内容不重新编码。旧版自定义目录在启动时通过 SQLite 快照和附件校验迁移，成功后移除原库和已迁移附件。移动软件时一起移动数据库与附件目录。

Windows / Android 客户端需要手动导出 ZIP；NAS 服务提供每日独立快照和手工备份命令，见 [NAS 备份说明](nas.md#数据与备份)。数据库内历史有助于恢复误操作，但数据库所在磁盘损坏仍会丢失历史，需要把快照保存在独立位置。
